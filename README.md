# DNS Server Tool for Windows-base DNS Servers

Простое WinForms-приложение для работы с DNS-сервером Windows (то, чего нет в оснастке `dnsmgmt.msc`):
зоны (AD-интегрированные и файловые), Zone Scopes, записи внутри scope (A/AAAA/CNAME/PTR/TXT/SRV),
клиентские подсети, Query Resolution Policies.

Работает через встроенный PowerShell-модуль `DnsServer` — приложение должно запускаться
**на самом DNS-сервере**, под администратором.

Автор: Kuzanov.e, 2026.

## Редактирование, проверка и удаление записи

Все действия над конкретной записью (вкладка "Scopes и записи") собраны в одном месте -
контекстное меню по **правой кнопке мыши** на записи в списке. Отдельных кнопок на панели
для этого больше нет - специально, чтобы не плодить кнопки на каждое действие.

- **Двойной клик** по записи (либо пункт **"Изменить запись..."** в меню) открывает окно
  редактирования: тип, имя, значение (+ Priority/Weight/Port для SRV).
  Модуль `DnsServer` не даёт надёжной команды "изменить запись на месте" сразу для всех
  типов, поэтому под капотом это **пересоздание**: сначала добавляется новая запись с
  новыми значениями, и только при успехе удаляется старая. Если добавление не удалось -
  старая запись остаётся нетронутой, ничего не теряется.
- **"Удалить запись..."** в том же меню - подтверждение (обычное окно да/нет, без
  усиленного 5-секундного таймера - тот зарезервирован для более тяжёлых операций вроде
  удаления целой зоны/scope/подсети/политики).
- **"Проверить запись..."** в том же меню открывает окно с двумя проверками:
  - **nslookup** (через `Resolve-DnsName`, но вывод причёсан под привычный вид консольного
    nslookup и переведён на русский - без служебного мусора вроде CIM-полей). Поле имени
    предзаполнено (уже с доменом зоны), редактируется. Поле сервера - если пусто, используется
    текущий целевой сервер приложения (см. "Целевой DNS-сервер" выше), если и там пусто -
    локальный резолвер.
  - **Ping** - обычный ICMP через `ping.exe`, 4 пакета по умолчанию (как классический ping) или
    непрерывно (флажок `-t`, с отдельной кнопкой "Стоп"). Если заполнено поле "Сервер" - оно
    подставляется как `-S` (адрес источника), полезно на многоинтерфейсной машине (например,
    сравнить внутренний адрес и NAT-адрес). Это работает только с адресами, реально принадлежащими этой машине.
  - Вывод `ping.exe` на русской Windows идёт в кодировке CP866 (иначе были бы "кракозябры") -
    учтено при чтении.

## Автоподгрузка списков зон

Список зон (вкладка "Зоны") и выпадающие списки зон (вкладки "Scopes и записи" и
"Политики") подгружаются автоматически при первом заходе на вкладку - не нужно нажимать
"Обновить" вручную на пустом списке. Если список уже не пуст (загружен раньше или обновлён
вручную) - повторного обращения к серверу при каждом переключении вкладки не происходит.

## Файловый режим для Secondary-зон (обходной путь)

Если зона на этом сервере - **Secondary** (реплика, read-only), а нужный scope существует
только локально (не реплицируется зонным трансфером с мастера - подробнее см. историю
разбора конкретного кейса ниже), обычная кнопка "Добавить запись" не сработает: DNS Server
API отказывает с `WIN32 9611 / "Недопустимый тип зоны DNS"`, потому что зона read-only.

Кнопка **"Добавить (файл, для Secondary-зон)"** под основной формой записи - обходной путь
именно для этого случая:
1. Строка дописывается **напрямую в `.dns`-файл scope** по пути
   `C:\Windows\System32\dns\<зона>\<scope>.dns` - **всегда локально**, на этой же машине,
   вне зависимости от настройки "Целевой сервер" сверху (суть в том, что физический файл
   лежит именно здесь).
2. Перед правкой автоматически делается бэкап файла (копия с таймстампом рядом).
3. Зона перезагружается командой `dnscmd /ZoneReload <зона>` - перечитывает файл с диска,
   не спрашивая, Primary зона или Secondary (в отличие от API добавления записи).

Это обходит нормальные проверки DNS Server, поэтому кнопка сопровождается explicit
предупреждением при каждом нажатии. Используй только когда точно понимаешь, что делаешь -
и после того, как проверено, что на мастере зоны такого scope нет (иначе это "осиротевший"
локальный артефакт, а не настоящая реплика - см. раздел про источник зоны выше).

## Сворачивание блока вывода

Кнопка "▲ Свернуть" / "▼ Показать" рядом с "Очистить" сворачивает блок вывода внизу окна
в одну строку с кнопками, не теряя накопленный текст (просто прячет, не очищает) - удобно,
когда список вывода большой и не хочется постоянно крутить колёсиком мыши мимо него.

## Версия и иконка

Версия приложения зашита в `AssemblyTitle` (в `DnsToolWinForms.csproj`) и в заголовке
главного окна, формат `v1.9.<N>` - число увеличивается на 1 при каждой правке, чтобы по
одному взгляду на окно/exe было видно, какая сборка сейчас развёрнута.

Иконка (`<ApplicationIcon>icon.ico</ApplicationIcon>` в csproj) используется и в exe, и в
заголовке **всех** окон приложения (главное окно и все диалоги - подтверждения удаления,
редактирование записи, проверка записи) через общий хелпер `AppIcon.cs`. **Файл `icon.ico`
должен реально лежать рядом с `.csproj`** - без него сборка упадёт с ошибкой (MSBuild не
найдёт файл для Win32-ресурса).

## Как открыть и собрать

1. Скачай папку `DnsToolWinForms` целиком на DNS-сервер.
2. Открой `DnsToolWinForms.csproj` в Visual Studio (2019/2022, поддержка SDK-style csproj).
3. Восстанови NuGet-пакеты (Visual Studio сделает это автоматически при открытии).
4. Для готового `.exe` переключи конфигурацию сверху с `Debug` на `Release` и собери
   (`Build → Build Solution`, `Ctrl+Shift+B`). Файл появится в `bin\Release\net48\DnsToolWinForms.exe`.
5. Запусти — приложение само запросит права администратора (UAC), это обязательно,
   иначе командлеты DnsServer вернут Access Denied.

Сборка `System.Management.Automation`, на которую ссылается проект, нужна только для
**компиляции** (берётся из reference-пакета) и не копируется рядом с exe — на рантайме
приложение находит настоящую сборку PowerShell прямо в Windows. Поэтому `.exe` можно
просто скопировать на сервер — ничего дополнительно ставить не надо.

### Если Windows Defender / антивирус ругается на exe

Это ожидаемо для неподписанного exe, который хостит PowerShell изнутри и просит права
администратора — типичные эвристические триггеры. Реальные варианты:
- подписать exe корпоративным code-signing сертификатом (`signtool.exe`);
- добавить exe/папку в исключения антивируса на самом сервере;
- отправить на проверку как false positive (для Kaspersky - https://opentip.kaspersky.com/).

## Если NuGet не найдёт пакет `Microsoft.PowerShell.5.1.ReferenceAssemblies`

В `DnsToolWinForms.csproj` есть закомментированный блок с прямой ссылкой (`HintPath`)
на системную сборку PowerShell 5.1. Раскомментируй его и убери `PackageReference` —
подробности прямо в файле csproj.

## Структура

- `Program.cs` — точка входа; здесь же при старте создаётся файл лога изменений.
- `MainForm.cs` — вся форма: 4 вкладки + общий блок вывода снизу + футер. Разметка строится
  кодом (без .resx/Designer.cs) через простые FlowLayoutPanel-хелперы `Row`/`Column`.
- `DnsHelper.cs` — обёртка над `System.Management.Automation`: вызывает командлеты через
  `AddCommand`/`AddParameter` (без склейки строк), разворачивает вложенные/массивные значения
  свойств в читаемый текст, вытаскивает реальный текст ошибки из `InnerException`/CIM-полей.
- `FileLogger.cs` — пишет файл `changes.log` рядом с exe.

## Вкладки

### Зоны
`Get-DnsServerZone`, `Add-DnsServerPrimaryZone`, `Remove-DnsServerZone`.

При создании новой зоны можно выбрать тип:
- **AD-интегрированная (реплика: домен)** — `-ReplicationScope Domain` (поведение по умолчанию);
- **AD-интегрированная (реплика: лес)** — `-ReplicationScope Forest`;
- **Файловая (.dns на диске)** — `-ZoneFile <имя>.dns`, без AD.

Список зон показывает короткую метку `[AD]` / `[файл]` рядом с именем (по свойству
`IsDsIntegrated`), чтобы сразу было видно, с чем имеешь дело.

### Scopes и записи
`Get/Add/Remove-DnsServerZoneScope`, плюс типизированные командлеты добавления записей:

| Тип   | Командлет                           | Параметр значения  |
|-------|-------------------------------------|--------------------|
| A     | `Add-DnsServerResourceRecordA`      | `-IPv4Address`     |
| AAAA  | `Add-DnsServerResourceRecordAAAA`   | `-IPv6Address`     |
| CNAME | `Add-DnsServerResourceRecordCName`  | `-HostNameAlias`   |
| PTR   | `Add-DnsServerResourceRecordPtr`    | `-PtrDomainName`   |
| TXT   | `Add-DnsServerResourceRecord -Txt`  | `-DescriptiveText` |
| SRV   | `Add-DnsServerResourceRecord -Srv`  | `-DomainName`      |

Важно: A/AAAA/CNAME/PTR используют **типизированные** командлеты, а не универсальный
`Add-DnsServerResourceRecord -A/-AAAA/...` — универсальный вариант в паре сценариев падал
с общей ошибкой без деталей, типизированные оказались надёжнее.

**TXT и SRV — исключение**: `Add-DnsServerResourceRecordTxt` и `Add-DnsServerResourceRecordSrv`
**не существуют** как отдельные командлеты (проверено по официальной документации Microsoft) —
для них обязательно используется универсальный `Add-DnsServerResourceRecord` с ключом `-Txt`/`-Srv`.
Если попытаться дёрнуть несуществующий типизированный командлет — `CommandNotFoundException`.

Для записи в корне зоны (SOA/NS/SPF-запись в TXT и т.п.) в поле имени укажи `@`.

Зона выбирается **выпадающим списком** (с возможностью подправить вручную) — список
подгружается автоматически при старте приложения, кнопка `↻ зоны` обновляет его вручную.

Список записей выводит **реальные значения** (IP, целевое имя, текст), а не имя .NET-типа —
`RecordData` у `Get-DnsServerResourceRecord` это вложенный CIM-объект, `DnsHelper.DescribeRecordData()`
достаёт из него нужное поле per-тип записи (для SRV показывает ещё и port/priority/weight).

### Особый случай при редактировании: смена типа на/с CNAME

DNS не позволяет CNAME сосуществовать с **любой** другой записью под тем же именем — ни на
секунду. Обычный безопасный порядок редактирования ("сначала добавить новую, потом удалить
старую" — так исходная запись не теряется при сбое) в этом случае **физически не сработает**:
сервер откажет добавлять новую запись, пока старая ещё жива под этим именем (код ошибки
`WIN32 9708 "Узел является записью CNAME DNS"`).

Если имя записи не меняется и хотя бы одна из сторон (старая или новая) — CNAME, приложение
автоматически переключается на обратный порядок: сначала удаляет старую запись, потом
добавляет новую. Если добавление новой не удалось — делается попытка **автоматического
отката** (вернуть старую запись назад), чтобы имя не осталось совсем без записи. Если и
откат не удался — это явно пишется в лог с пометкой "записи нет, добавь вручную".

Удаление записи передаёт **весь объект целиком** через `-InputObject`
(`Get-DnsServerResourceRecord | Remove-DnsServerResourceRecord`) — так надёжнее, чем
собирать `-RecordData` вручную.

### Подсети
`Get/Add/Remove-DnsServerClientSubnet`. Список показывает имя + реальный CIDR.

### Политики
`Get/Add/Remove-DnsServerQueryResolutionPolicy`.

**Важная особенность**, выясненная опытным путём: у объекта, который возвращает
`Get-DnsServerQueryResolutionPolicy`, подсеть лежит в свойстве **`Criteria`**, а
scope — в свойстве **`Content`**. Свойств `ClientSubnet`/`ZoneScope` в возвращаемом
объекте не существует — это имена **параметров** у `Add-DnsServerQueryResolutionPolicy`,
но не имена свойств у результата `Get-...`. Модуль называет вход и выход по-разному.

Список политик показывает только имена (компактно, без переполнения строки); справа —
панель с подробностями выбранной политики, где подсети подсвечены зелёным, а scope синим.
Имена подсетей в `Criteria` дополнительно резолвятся в реальный CIDR (запрос
`Get-DnsServerClientSubnet` и сопоставление имя → диапазон).

Создание политики поддерживает несколько подсетей через запятую (логическое ИЛИ):
```
-ClientSubnet "EQ,net_100,Old_DNS_redirect13,Old_DNS_redirect6"
```

## Удалённое управление другим DNS-сервером

Приложение по умолчанию работает с локальной службой DNS (там же, где запущено). Но
сверху окна есть поле **"Целевой DNS-сервер"** — если вписать туда имя/IP другого сервера,
**все** операции на всех вкладках начинают выполняться на нём через `-ComputerName`
(этот параметр поддерживают практически все командлеты модуля `DnsServer`) — без
переноса самого приложения на тот сервер.

Актуально, например, когда нужная зона на текущем сервере — `Secondary` (read-only
реплика), а редактировать можно только на её `Primary`-сервере (мастере). Вместо того
чтобы копировать exe туда, можно один раз указать адрес мастера в этом поле.

Чтобы это заработало:
- на целевом сервере должен быть включён **WinRM** (обычно уже включён на Windows Server
  по умолчанию; если нет — `Enable-PSRemoting` на нём самом);
- файрвол должен пропускать WinRM (TCP 5985) между твоей машиной и целевым сервером;
- учётка, под которой запущено приложение, должна иметь права на управление DNS на
  целевом сервере (то же самое, что нужно и для локальной работы) — если лес/домен и
  учётка те же, Kerberos-аутентификация проходит прозрачно, ничего доп. настраивать не нужно.

Кнопка "Проверить подключение" рядом с полем делает пробный `Get-DnsServerZone` и
показывает в логе, получилось достучаться или нет.

Оставь поле пустым — и всё вернётся к работе с локальным сервером, как раньше.

## Подтверждение удаления

Удаление одиночной записи (A/AAAA/CNAME/...) — обычное окно "да/нет", без лишней драмы.

Удаление **зоны, scope, подсети или политики** — усиленное окно (`DangerConfirmDialog.cs`):
крупный красный текст с описанием последствий, кнопка "Удалить" заблокирована первые
5 секунд с видимым отсчётом (5...4...3...2...1) — специально, чтобы нельзя было кликнуть
на автомате не глядя. Кнопка "Отмена" активна сразу.

## Списки с перетаскиваемой границей

На вкладках "Scopes и записи" и "Политики" граница между двумя панелями (списком и
деталями/записями) — перетаскиваемая (`SplitContainer`). Позиция сохраняется в
`settings.ini` рядом с exe и восстанавливается при следующем запуске (по ключам
`ScopesRecordsSplitter` и `PoliciesSplitter`). Если файл настроек недоступен или
повреждён — просто используется позиция по умолчанию, ничего не падает.

## Сортировка, фильтр и экспорт списков

На вкладках "Зоны" и "Scopes и записи" (список записей) есть:
- **Фильтр** — текстовое поле, список сужается по мере ввода (ищет по всем видимым полям
  строки: имени, типу, значению/метке). Работает мгновенно, без обращения к серверу —
  фильтрует то, что уже загружено.
- **Сортировка** — выпадающий список поля (Имя/Тип/[Значение]) + кнопка ▲/▼ для смены
  направления.
- **Экспорт в файл...** — сохраняет то, что сейчас реально отображено в списке (то есть
  уже с учётом фильтра и сортировки) в `.txt`, путь выбирается стандартным диалогом
  сохранения. Есть также на вкладке "Подсети".

Важно для записей в scope: сортировка/фильтр меняют порядок строк на экране, но не путают
удаление — приложение ведёт отдельный список "что сейчас реально показано" и удаляет именно
ту запись, что выбрана, а не то, что было бы по номеру в исходном (несортированном) ответе сервера.

## Источник зоны

На вкладке "Зоны" под списком — полоса с информацией об источнике выбранной зоны:
- для `Primary` — AD (домен) или файл (`.dns`, с указанием имени);
- для `Secondary`/`Stub` — список мастер-серверов (`MasterServers`), с которых зона
  реплицируется. Такую зону нельзя редактировать здесь вообще — редактировать нужно
  на одном из перечисленных мастеров (см. раздел про "Целевой DNS-сервер" выше).

## История удалённых серверов

Поле "Целевой DNS-сервер" запоминает последние 10 серверов, к которым приложение успешно
подключалось (и локально это не считается) — при переключении с "Локальный" на ручной
ввод сразу открывается выпадающий список с этой историей, не нужно перепечатывать адрес
каждый раз заново. Хранится в `settings.ini` рядом с exe.

## Файл лога изменений

`changes.log` лежит **рядом с exe**, создаётся автоматически при первом запуске
приложения (если уже есть — не трогается и просто дополняется). Пишутся только реальные
изменения (создание/удаление зоны, scope, подсети, политики, записи) — без "шума" от
обновления списков. Размер файла не ограничивается.

Формат строки:
```
2026-07-16 14:04:32 | OK     | RECORD ADD    | зона/объект: corp.local | Scope=... A test -> 10.0.0.1 | пользователь: admin
```

Кнопка "Открыть файл лога изменений" в панели вывода открывает файл в ассоциированной
программе (обычно блокнот).

## Диагностика ошибок

- Если PowerShell-командлет бросает исключение, в лог попадает **вся цепочка**
  `InnerException` плюс, через рефлексию, доп. поля вроде `StatusCode`/`NativeErrorCode`/
  `ErrorData` (там у CIM-исключений обычно прячется настоящая причина, а не generic-фраза
  "Не удалось создать запись ресурса...").
- Если после запроса политики поле подсети/scope пустое — приложение автоматически
  выводит в лог **все реальные свойства** объекта, чтобы можно было увидеть точные
  имена без гаданий (см. историю про `Criteria`/`Content` выше).
