# DnsToolWinForms

Простое WinForms-приложение для работы с DNS-сервером Windows (то, чего нет в оснастке `dnsmgmt.msc`):
зоны (AD-интегрированные и файловые), Zone Scopes, записи внутри scope (A/AAAA/CNAME/PTR/TXT/SRV),
клиентские подсети, Query Resolution Policies.

Работает через встроенный PowerShell-модуль `DnsServer` — приложение должно запускаться
**на самом DNS-сервере**, под администратором.

Автор: foosber, 2026.

## Требования

- **.NET Framework 4.8** (target framework проекта — `net48`, см. `DnsToolWinForms.csproj`).
  На большинстве Windows Server (2016+) он уже установлен «из коробки»; если нет —
  ставится через `Установка и удаление программ → Дополнительные компоненты` или
  скачивается отдельно с сайта Microsoft.
- **Windows Server с ролью DNS Server** — приложение работает через встроенный
  PowerShell-модуль `DnsServer`, который есть только там, где эта роль установлена
  (либо через RSAT: DNS Server Tools на клиентской машине для удалённого управления).
- **Права локального администратора** для запуска (обязательно, см. `app.manifest`).
- **Visual Studio 2019/2022** — только для сборки из исходников (не нужна, если просто
  используешь готовый `.exe` из Releases).

## Редактирование, проверка и удаление записи

Все действия над конкретной записью (вкладка "Scopes и записи") собраны в одном месте -
контекстное меню по **правой кнопке мыши** на записи в списке. Отдельных кнопок на панели
для этого больше нет - специально, чтобы не плодить кнопки на каждое действие.

- **Двойной клик** по записи (либо пункт **"Изменить запись..."** в меню) открывает окно
  редактирования: тип, имя, значение (+ Priority/Weight/Port для SRV).
  Модуль `DnsServer` не даёт надёжной команды "изменить запись на месте" сразу для всех
  типов, поэтому под капотом это **пересоздание**: сначала добавляется новая запись с
  новыми значениями, и только при успехе удаляется старая. Если добавление не удалось -
  старая запись остаётся нетронутой, ничего не теряется.
- **"Удалить запись..."** в том же меню - подтверждение (обычное окно да/нет, без
  усиленного 5-секундного таймера - тот зарезервирован для более тяжёлых операций вроде
  удаления целой зоны/scope/подсети/политики).
- **"Проверить запись..."** в том же меню открывает окно с двумя проверками:
  - **nslookup** (через `Resolve-DnsName`, но вывод причёсан под привычный вид консольного
    nslookup и переведён на русский - без служебного мусора вроде CIM-полей). Поле имени
    предзаполнено (уже с доменом зоны), редактируется. Поле сервера - если пусто, используется
    текущий целевой сервер приложения (см. "Целевой DNS-сервер" выше), если и там пусто -
    локальный резолвер.
  - **Ping** - обычный ICMP через `ping.exe`, 4 пакета по умолчанию (как классический ping) или
    непрерывно (флажок `-t`, с отдельной кнопкой "Стоп"). Если заполнено поле "Сервер" - оно
    подставляется как `-S` (адрес источника), полезно на многоинтерфейсной машине (например,
    сравнить внутренний адрес и NAT-адрес). Это не "запустить ping с другого сервера" - в Windows
    нет линуксового `-I`, `-S` работает только с адресами, реально принадлежащими этой машине.
  - Вывод `ping.exe` на русской Windows идёт в кодировке CP866 (иначе были бы "кракозябры") -
    учтено при чтении.

## Автоподгрузка списков зон

Список зон (вкладка "Зоны") и выпадающие списки зон (вкладки "Scopes и записи" и
"Политики") подгружаются автоматически при первом заходе на вкладку - не нужно нажимать
"Обновить" вручную на пустом списке. Если список уже не пуст (загружен раньше или обновлён
вручную) - повторного обращения к серверу при каждом переключении вкладки не происходит.

## Файловый режим для Secondary-зон (обходной путь)

Если зона на этом сервере - **Secondary** (реплика, read-only), а нужный scope существует
только локально (не реплицируется зонным трансфером с мастера - подробнее см. историю
разбора конкретного кейса ниже), обычная кнопка "Добавить запись" не сработает: DNS Server
API отказывает с `WIN32 9611 / "Недопустимый тип зоны DNS"`, потому что зона read-only.

Кнопка **"Добавить (файл, для Secondary-зон)"** под основной формой записи - обходной путь
именно для этого случая:
1. Строка дописывается **напрямую в `.dns`-файл scope** по пути
   `C:\Windows\System32\dns\<зона>\<scope>.dns` - **всегда локально**, на этой же машине,
   вне зависимости от настройки "Целевой сервер" сверху (суть в том, что физический файл
   лежит именно здесь).
2. Перед правкой автоматически делается бэкап файла (копия с таймстампом рядом).
3. Зона перезагружается командой `dnscmd /ZoneReload <зона>` - перечитывает файл с диска,
   не спрашивая, Primary зона или Secondary (в отличие от API добавления записи).

Это обходит нормальные проверки DNS Server, поэтому кнопка сопровождается explicit
предупреждением при каждом нажатии. Используй только когда точно понимаешь, что делаешь -
и после того, как проверено, что на мастере зоны такого scope нет (иначе это "осиротевший"
локальный артефакт, а не настоящая реплика - см. раздел про источник зоны выше).

## Сворачивание блока вывода

Кнопка "▲ Свернуть" / "▼ Показать" рядом с "Очистить" сворачивает блок вывода внизу окна
в одну строку с кнопками, не теряя накопленный текст (просто прячет, не очищает) - удобно,
когда список вывода большой и не хочется постоянно крутить колёсиком мыши мимо него.

## Версия и иконка

Версия приложения зашита в `AssemblyTitle` (в `DnsToolWinForms.csproj`) и в заголовке
главного окна, формат `v1.9.<N>` - число увеличивается на 1 при каждой правке, чтобы по
одному взгляду на окно/exe было видно, какая сборка сейчас развёрнута.

Иконка (`<ApplicationIcon>icon.ico</ApplicationIcon>` в csproj) используется и в exe, и в
заголовке **всех** окон приложения (главное окно и все диалоги - подтверждения удаления,
редактирование записи, проверка записи) через общий хелпер `AppIcon.cs`. **Файл `icon.ico`
должен реально лежать рядом с `.csproj`** - без него сборка упадёт с ошибкой (MSBuild не
найдёт файл для Win32-ресурса).

## Минимизация интерфейса: иконки вместо полей (v2.2.0)

Все текстовые кнопки на всех 4 вкладках (Зоны, Scopes и записи, Подсети, Политики) заменены
на компактные кнопки-иконки: обновить, добавить, удалить, экспорт и т.п. Иконки —
собственные, рисуются через GDI+ (`IconFactory.cs`), не шрифт и не внешние файлы — тот же
приём, что уже использовался для круглого значка "?" (`HelpIcon.cs`).

Действия, которым раньше требовались всегда видимые текстовые поля на панели (создать зону,
создать scope, добавить запись, создать подсеть, создать политику), теперь открывают
маленькое диалоговое окно при клике на иконку "+" — поля видны только тогда, когда реально
нужны. Бизнес-логика (`AddZoneAsync`, `AddScopeAsync`, `AddRecordToScopeAsync` и т.п.) не
менялась вообще — диалоги просто заполняют те же самые (теперь скрытые) поля перед вызовом
уже существующих методов.

**Что осталось как было**: фильтр записей/зон — по-прежнему обычное текстовое поле прямо на
панели (не за диалогом), потому что живой поиск по мере набора текста ценнее компактности.
Двойной клик по записи (редактирование) и правая кнопка мыши (меню проверить/изменить/удалить,
и на дереве — создать папку) работают ровно так же, как в v2.1.0, без изменений.

## Двойной клик по зоне -> сразу к её scope'ам (v2.2.2)

Двойной клик по зоне на вкладке "Зоны" переключает на вкладку "Scopes и записи" с этой
зоной уже выбранной и её scope'ами загруженными — не нужно переключаться вручную и
подставлять имя зоны в выпадающий список. Порядок операций специально выстроен так, чтобы
не столкнуться гонкой с собственным автообновлением вкладки "Scopes и записи" (которое
само подгружает список зон при первом заходе, если он ещё пуст, см. раздел "Автоподгрузка
списков зон" ниже) — сначала полностью загружаются данные, и только потом переключается
вкладка.

## Дерево записей (v2.1.0)

Вкладка "Scopes и записи" — теперь **единое дерево** слева вместо отдельных списка scope'ов
и списка записей. Верхний уровень дерева — scope'ы зоны; внутри каждого — записи,
сгруппированные по составным именам в "папки", по аналогии с `dnsmgmt.msc`: например запись
`admin.pro32connect` попадает в папку `pro32connect` как элемент `admin`; запись
`_ldap._tcp.dc._msdcs` — в путь `_msdcs > dc > _tcp > _ldap`.

- **Ленивая подгрузка scope**: записи конкретного scope загружаются только при первом
  выборе/раскрытии его узла в дереве — не все scope'ы сразу. Некоторые scope содержат
  сотни записей, незачем тянуть их все, если реально смотрят один.
- Группировка по папкам строится **из уже загруженных данных** этого scope, без
  дополнительных обращений к серверу — DNS Server как отдавал плоский список, так и отдаёт,
  "папки" существуют только в интерфейсе.
- Справа — список текущей выбранной "папки" (или scope, если выбран его корень): **и
  подпапки, и собственные записи этого уровня вместе**.
- Двойной клик по строке-папке справа **или** клик по узлу дерева слева — заходит внутрь,
  показывая её содержимое.
- Внутри любой папки продолжают работать **все** прежние функции без изменений: фильтр,
  сортировка, экспорт, двойной клик для редактирования записи, правая кнопка мыши
  (проверить/изменить/удалить) — они применяются к содержимому текущей папки, а не ко
  всему scope сразу.
- Попытка удалить/проверить **папку** (а не запись) через контекстное меню вежливо
  отклоняется с понятным сообщением; двойной клик или "Изменить запись..." по папке вместо
  этого просто заходит внутрь.
- Создание/удаление scope и добавление записи по-прежнему используют поле "Записи scope" —
  оно теперь автоматически синхронизируется с тем, какой scope открыт в дереве, при любой
  навигации, включая переход между вложенными папками одного и того же scope.
- Позиция границы между деревом и списком запоминается в `settings.ini`
  (`RecordsTreeSplitter`), как и остальные перетаскиваемые границы в приложении.

### Добавление записи учитывает текущую папку

Если ты находишься внутри папки (например `pro32connect`) и добавляешь запись с именем
`test`, реальное имя записи станет `test.pro32connect`, а не просто `test` в корне scope —
над формой добавления есть подсказка "Добавление в: ...", показывающая, куда именно попадёт
новая запись. `@` внутри папки означает "сама эта папка" (запись без дополнительной метки).

### Создание "папки" (поддомена) через wildcard

Папки в дереве — чисто визуальная группировка по именам записей (см. выше), без хотя бы
одной записи внутри папка не существует. Правая кнопка мыши на scope или уже существующей
папке → "Создать папку (поддомен, \* + IP)..." — создаёт wildcard-запись `*` внутри нового
поддомена (например `*.sales` → IP). Это одновременно настоящая DNS-запись (отвечает на
любое имя внутри этого поддомена) и способ сделать поддомен видимым как папку в дереве.

### Фикс: обычные записи больше не маскировались под папки

`BuildRecordTree` создаёт узел дерева для каждого сегмента составного имени, включая
последний ("лист") — то есть у записи `admin.pro32connect` появлялся узел `admin` внутри
`pro32connect`, даже если `admin` — это просто обычная запись, а не настоящая папка. Раньше
и дерево слева, и правый список считали **любой** дочерний узел "папкой" (с иконкой 📁 и
счётчиком "N записей"), не отличая узел с реальной вложенностью от рядовой записи. Теперь
критерий "это настоящая папка" — **у узла есть свои дочерние узлы** (что-то вложено ещё
глубже); одноуровневые записи показываются как обычные записи (тип, значение), а не
маскируются под папки, и не засоряют дерево слева лишними ветками. Проверено на реальном
scope с 454 записями: 380 корневых узлов, из них 14 настоящих папок и 366 узлов-листьев —
в дереве корректно остались только эти 14.

## Проверка и установка обновлений (v2.0.3, фикс гонки в v2.0.5)

**Известная и исправленная проблема (v2.0.5)**: раньше `.bat`-обновлятор ждал перед копированием
фиксированные 2 секунды, чего иногда не хватало, чтобы процесс приложения реально закрылся
и отпустил файл `.exe` (`Application.Exit()` не гарантирует мгновенное завершение - закрытие
`CimSession`, финализаторы и т.п. могут занять больше времени). Если `.exe` оставался
заблокированным, `robocopy` молча не мог его перезаписать, а скрипт всё равно шёл дальше и
запускал СТАРЫЙ `.exe` - выглядело как "обновление прошло, но версия осталась старой".
Теперь вместо фиксированной паузы - реальный опрос через `tasklist`, жив ли ещё процесс
(раз в секунду, с пределом в 30 секунд на всякий случай), и `robocopy` получил больше попыток
на подстраховку (`/R:10` вместо `/R:3`).

Кнопка "Проверить обновления" в окне "О программе" тянет последний релиз с GitHub
(`GET /repos/foosber-byte/dnstool/releases/latest`), сравнивает версию с текущей
(`AppVersion.cs` — единственное место, где хранится версия, вместе с `AssemblyTitle`
в `.csproj`). Если новее — предлагает скачать и установить, ничего не делая без
подтверждения.

**Требование**: серверу, на котором запущено приложение, нужен исходящий HTTPS-доступ к
`github.com`/`api.github.com`. Если сервер в закрытом сегменте сети (частый случай для
DNS-серверов в защищённой инфраструктуре) — проверка честно вернёт ошибку с понятным
текстом, а не зависнет молча.

**Как устроено самообновление**: Windows не даёт перезаписать свой же запущенный `.exe`
напрямую. Поэтому: архив релиза скачивается и распаковывается во временную папку, там же
готовится маленький `.bat`-скрипт, который через пару секунд (когда приложение уже
закроется) копирует новые файлы поверх текущих через `robocopy`, перезапускает `.exe` и
подчищает за собой временную папку. `.bat` запускается, и только после этого текущий
процесс завершается (`Application.Exit()`) — тогда файл `.exe` освобождается для перезаписи.

**`settings.ini`, `changes.log` и `*.dns`-файлы зон не трогаются** — они явно исключены из
копирования (`robocopy /XF settings.ini changes.log changes.log.bak_* *.dns *.dns.bak_*`).
Это работает надёжно ещё и потому, что эти файлы вообще не входят в архив релиза
(они в `.gitignore`, создаются только в рантайме) — исключение в `robocopy` просто
дополнительная подстраховка, а не единственная защита.

Каждая попытка обновления (успешная или нет) фиксируется в `changes.log`.

## Подсказки как значки "?" (v2.0.1)

Все текстовые подсказки под полями (серый курсивный текст) заменены на маленькие круглые
значки "?" — подсказка показывается только при наведении курсора (обычный Windows
`ToolTip`), а не занимает место в интерфейсе постоянно. Значок круглый, светло-синий
пастельный (не резкий яркий цвет) — общий хелпер `HelpIcon.cs`, используется во всех
окнах (главное окно, проверка записи, редактирование записи, аутентификация). Заодно все
затронутые диалоги стали компактнее по высоте — освободившееся место убрано, а не просто
оставлено пустым.

## Перезагрузка зоны (v2.0.1)

Кнопка "Перезагрузить зону" на вкладке "Зоны" — перечитывает выбранную зону с диска
(`dnscmd /ZoneReload`) без перезапуска всей службы DNS. Полезно, если запись поправили в
обход приложения (руками в файле) и нужно, чтобы DNS Server подхватил изменения. Как и
файловый режим для Secondary-зон, эта команда выполняется **всегда локально** (на этой же
машине, через `Process.Start("dnscmd.exe")`) — не учитывает настройку "Целевой сервер"
сверху, потому что `dnscmd.exe` не умеет обращаться к другим серверам через WinRM.

## Аутентификация на удалённом сервере (v2.0)

Если проверка подключения к целевому серверу не проходит текущей Windows-учёткой (например,
у неё просто нет прав именно на этом сервере) - автоматически открывается окно
аутентификации: логин, пароль, чекбокс "Подключаться через HTTPS" (WinRM/5986 вместо
WinRM/5985, требует HTTPS-листенер и валидный сертификат на сервере). Зелёный "OK" с
автозакрытием при успехе, красная ошибка с возможностью повторить при неудаче.

Технически: у командлетов модуля `DnsServer` **нет** параметра `-Credential` (только
`-ComputerName`/`-CimSession`) - единственный официальный способ работать под другой
учёткой - создать `CimSession` через `New-CimSession -Credential` и передавать её вместо
`-ComputerName` во все дальнейшие вызовы. Именно так это и реализовано; сессия кэшируется
и автоматически используется, пока не сменится целевой сервер или не закроется приложение
(тогда она явно закрывается, чтобы не оставлять висящие WinRM-подключения на сервере).

Про хеширование пароля: пароль **не хешируется перед отправкой** - Kerberos/NTLM (то, что
реально использует WinRM) сам по себе является challenge-response протоколом, пароль по сети
не передаётся вообще, ни в открытом, ни в хешированном виде. Клиентское хеширование тут не
только не нужно, а физически сломало бы аутентификацию (сервер ждёт ответ на вызов,
посчитанный от настоящего пароля). Реально снижает риск - HTTPS (см. чекбокс выше) и то, что
пароль строится сразу в память как `SecureString` посимвольно, минуя лишнюю копию в виде
обычной строки.

Каждая попытка (успешная или нет) пишется в `changes.log` через запись `AUTH` - без пароля.

### Фикс диагностики: реальная причина ошибки вместо generic-сообщения (v2.1.0)

Раньше при любой неудаче показывалось жёстко зашитое "Ошибка логина или пароля", даже если
причина была вообще не в них (например, проблема WinRM/сети). Причина: `New-CimSession`
вызывается с `-ErrorAction Stop`, и PowerShell в этом случае оборачивает РЕАЛЬНУЮ причину в
`ActionPreferenceStopException`, у которого настоящая ошибка лежит не в обычном
`.InnerException`, а в `.ErrorRecord` (интерфейс `IContainsErrorRecord`). `DescribeException`
теперь разворачивает и это тоже - рекурсивно, на случай если внутри `ErrorRecord` ещё один
`CimException` со своими деталями. Диалог аутентификации теперь показывает реальный текст
причины (в прокручиваемом текстовом поле, чтобы длинная диагностика не обрезалась и её можно
было скопировать), а не всегда одну и ту же фразу про пароль.

### HTTPS и пропуск проверки сертификата — добавлены в v2.1.0, убраны в v2.2.1

В v2.1.0 в окно аутентификации добавлялись чекбоксы "Подключаться через HTTPS" и
"Пропустить проверку сертификата" (для случаев подключения по IP, где сертификат сервера
не совпадает по CN). На практике HTTPS-путь давал непредсказуемые результаты в зависимости
от конкретного сервера — то ошибка сертификата, то (даже с пропуском проверки) сервер
отвечал "Отказано в доступе" уже после успешного TLS-рукопожатия, то есть дело было в
конфигурации HTTPS-листенера WinRM на конкретной машине, а не в чём-то, что можно
исправить в самом приложении.

Убрано в v2.2.1: обычный путь (Kerberos, либо NTLM через `TrustedHosts` на клиенте) —
единственный проверенный и стабильно работающий, к тому же это ровно то же самое, что
использует штатный `Enter-PSSession`/`dnsmgmt.msc` при удалённом управлении — никакого
нестандартного протокола. Флаг "пропустить проверку сертификата" по своей природе снижает
защиту транспорта (принимает подмену сервера без предупреждения) и не был нужен на практике,
поэтому убран целиком, а не просто выключен — меньше поверхность для вопросов при разборе
кода. Подробности - см. `SECURITY.md`.

### Подсказка: WinRM не может достучаться до сервера вообще

Отдельная ошибка ("WinRM не удается выполнить операцию... компьютер доступен по сети...
брандмауэре...") означает, что дело не в логине/пароле, а в том, что WinRM в принципе не
может дозвониться. Приложение подсказывает три вещи для проверки: имя/IP резолвится
и доступно (проверь `ping` с этой же машины), служба WinRM реально запущена на целевом
сервере (`winrm quickconfig`), и сетевой профиль адаптера на целевом сервере — не
"Общедоступная сеть" (для профиля Public правило файрвола WinRM по умолчанию разрешает
подключения только из той же подсети).

### Фикс: CimSession "ликвидировалась" сразу после создания (v2.1.0)

После успешной аутентификации следующий же реальный запрос (например `Get-DnsServerZone`)
падал с `ObjectDisposedException: Доступ к ликвидированному объекту невозможен`. Причина:
`New-CimSession` вызывался через `using var ps = PowerShell.Create()` — созданная сессия,
судя по всему, привязывается командлетом к своему PowerShell-раннспейсу, и `Dispose()`
этого раннспейса (срабатывающий сразу по выходу из метода благодаря `using`) утаскивал за
собой и саму `CimSession`, хотя формально она ещё была нужна для дальнейших запросов.
Исправлено: раннспейс, создавший активную сессию, теперь держится живым (без `using`,
освобождается вручную) ровно столько же, сколько живёт сама сессия — оба освобождаются
вместе в `DisposeActiveCimSession()`.

## NS и MX записи (v2.0)

Добавлены к уже имевшимся A/AAAA/CNAME/PTR/TXT/SRV. NS - через универсальный
`Add-DnsServerResourceRecord -NS -NameServer` (выделенного командлета не существует).
MX - **имеет** выделенный командлет, `Add-DnsServerResourceRecordMX -MailExchange -Preference`
(это было отдельно перепроверено по документации Microsoft, чтобы не повторить ошибку с TXT/SRV).

## Исправление: многоуровневые имена записей (v2.0)

Раньше запись с именем вида `bla.bla` в зоне `corp.local` создавалась как
`bla.bla.corp.local.corp.local` (зона задваивалась), если в поле имени вводили запись
целиком, с доменом. Причина - DNS-командлеты ждут имя **относительно зоны** и сами
дописывают зону при создании. Добавлена нормализация (`NormalizeRecordName`) - если введено
имя с суффиксом зоны, суффикс срезается перед отправкой командлету; если введено имя,
совпадающее с зоной целиком, оно трактуется как `@` (корень зоны). Работает во всех трёх
путях создания/правки записи (обычное добавление, файловый режим, редактирование).

## Как открыть и собрать

1. Скачай папку `DnsToolWinForms` целиком на DNS-сервер.
2. Открой `DnsToolWinForms.csproj` в Visual Studio (2019/2022, поддержка SDK-style csproj).
3. Восстанови NuGet-пакеты (Visual Studio сделает это автоматически при открытии).
4. Для готового `.exe` переключи конфигурацию сверху с `Debug` на `Release` и собери
   (`Build → Build Solution`, `Ctrl+Shift+B`). Файл появится в `bin\Release\net48\DnsToolWinForms.exe`.
5. Запусти — приложение само запросит права администратора (UAC), это обязательно,
   иначе командлеты DnsServer вернут Access Denied.

Сборка `System.Management.Automation`, на которую ссылается проект, нужна только для
**компиляции** (берётся из reference-пакета) и не копируется рядом с exe — на рантайме
приложение находит настоящую сборку PowerShell прямо в Windows. Поэтому `.exe` можно
просто скопировать на сервер — ничего дополнительно ставить не надо.

### Если Windows Defender / антивирус ругается на exe

## Вкладки

### Зоны
`Get-DnsServerZone`, `Add-DnsServerPrimaryZone`, `Remove-DnsServerZone`.

При создании новой зоны можно выбрать тип:
- **AD-интегрированная (реплика: домен)** — `-ReplicationScope Domain` (поведение по умолчанию);
- **AD-интегрированная (реплика: лес)** — `-ReplicationScope Forest`;
- **Файловая (.dns на диске)** — `-ZoneFile <имя>.dns`, без AD.

Список зон показывает короткую метку `[AD]` / `[файл]` рядом с именем (по свойству
`IsDsIntegrated`), чтобы сразу было видно, с чем имеешь дело.

### Scopes и записи
`Get/Add/Remove-DnsServerZoneScope`, плюс типизированные командлеты добавления записей:

| Тип   | Командлет                          | Параметр значения |
|-------|-------------------------------------|--------------------|
| A     | `Add-DnsServerResourceRecordA`      | `-IPv4Address`     |
| AAAA  | `Add-DnsServerResourceRecordAAAA`   | `-IPv6Address`     |
| CNAME | `Add-DnsServerResourceRecordCName`  | `-HostNameAlias`   |
| PTR   | `Add-DnsServerResourceRecordPtr`    | `-PtrDomainName`   |
| NS    | `Add-DnsServerResourceRecord -NS`   | `-NameServer`      |
| MX    | `Add-DnsServerResourceRecordMX`     | `-MailExchange` (+ `-Preference`) |
| TXT   | `Add-DnsServerResourceRecord -Txt`  | `-DescriptiveText` |
| SRV   | `Add-DnsServerResourceRecord -Srv`  | `-DomainName`      |

Важно: A/AAAA/CNAME/PTR/**MX** используют **типизированные** командлеты, а не универсальный
`Add-DnsServerResourceRecord -A/-AAAA/...` — универсальный вариант в паре сценариев падал
с общей ошибкой без деталей, типизированные оказались надёжнее.

**TXT, SRV и NS — исключение**: `Add-DnsServerResourceRecordTxt`, `...Srv` и `...NS`
**не существуют** как отдельные командлеты (проверено по официальной документации Microsoft) —
для них обязательно используется универсальный `Add-DnsServerResourceRecord` с ключом
`-Txt`/`-Srv`/`-NS`. Если попытаться дёрнуть несуществующий типизированный командлет —
`CommandNotFoundException`. MX, наоборот, **имеет** выделенный командлет — легко было по
инерции отправить его туда же, что и NS, поэтому его существование отдельно перепроверено.

Для записи в корне зоны (SOA/NS/SPF-запись в TXT и т.п.) в поле имени укажи `@`.

Зона выбирается **выпадающим списком** (с возможностью подправить вручную) — список
подгружается автоматически при старте приложения, кнопка `↻ зоны` обновляет его вручную.

Список записей выводит **реальные значения** (IP, целевое имя, текст), а не имя .NET-типа —
`RecordData` у `Get-DnsServerResourceRecord` это вложенный CIM-объект, `DnsHelper.DescribeRecordData()`
достаёт из него нужное поле per-тип записи (для SRV показывает ещё и port/priority/weight).

### Особый случай при редактировании: смена типа на/с CNAME

DNS не позволяет CNAME сосуществовать с **любой** другой записью под тем же именем — ни на
секунду. Обычный безопасный порядок редактирования ("сначала добавить новую, потом удалить
старую" — так исходная запись не теряется при сбое) в этом случае **физически не сработает**:
сервер откажет добавлять новую запись, пока старая ещё жива под этим именем (код ошибки
`WIN32 9708 "Узел является записью CNAME DNS"`).

Если имя записи не меняется и хотя бы одна из сторон (старая или новая) — CNAME, приложение
автоматически переключается на обратный порядок: сначала удаляет старую запись, потом
добавляет новую. Если добавление новой не удалось — делается попытка **автоматического
отката** (вернуть старую запись назад), чтобы имя не осталось совсем без записи. Если и
откат не удался — это явно пишется в лог с пометкой "записи нет, добавь вручную".

Удаление записи передаёт **весь объект целиком** через `-InputObject`
(`Get-DnsServerResourceRecord | Remove-DnsServerResourceRecord`) — так надёжнее, чем
собирать `-RecordData` вручную.

### Подсети
`Get/Add/Remove-DnsServerClientSubnet`. Список показывает имя + реальный CIDR.

### Политики
`Get/Add/Remove-DnsServerQueryResolutionPolicy`.

**Важная особенность**, выясненная опытным путём: у объекта, который возвращает
`Get-DnsServerQueryResolutionPolicy`, подсеть лежит в свойстве **`Criteria`**, а
scope — в свойстве **`Content`**. Свойств `ClientSubnet`/`ZoneScope` в возвращаемом
объекте не существует — это имена **параметров** у `Add-DnsServerQueryResolutionPolicy`,
но не имена свойств у результата `Get-...`. Модуль называет вход и выход по-разному.

Список политик показывает только имена (компактно, без переполнения строки); справа —
панель с подробностями выбранной политики, где подсети подсвечены зелёным, а scope синим.
Имена подсетей в `Criteria` дополнительно резолвятся в реальный CIDR (запрос
`Get-DnsServerClientSubnet` и сопоставление имя → диапазон).

Создание политики поддерживает несколько подсетей через запятую (логическое ИЛИ):
```
-ClientSubnet "EQ,net_100,Old_DNS_redirect13,Old_DNS_redirect6"
```

## Удалённое управление другим DNS-сервером

Приложение по умолчанию работает с локальной службой DNS (там же, где запущено). Но
сверху окна есть поле **"Целевой DNS-сервер"** — если вписать туда имя/IP другого сервера,
**все** операции на всех вкладках начинают выполняться на нём через `-ComputerName`
(этот параметр поддерживают практически все командлеты модуля `DnsServer`) — без
переноса самого приложения на тот сервер.

Актуально, например, когда нужная зона на текущем сервере — `Secondary` (read-only
реплика), а редактировать можно только на её `Primary`-сервере (мастере). Вместо того
чтобы копировать exe туда, можно один раз указать адрес мастера в этом поле.

Чтобы это заработало:
- на целевом сервере должен быть включён **WinRM** (обычно уже включён на Windows Server
  по умолчанию; если нет — `Enable-PSRemoting` на нём самом);
- файрвол должен пропускать WinRM (TCP 5985) между твоей машиной и целевым сервером;
- учётка, под которой запущено приложение, должна иметь права на управление DNS на
  целевом сервере (то же самое, что нужно и для локальной работы) — если лес/домен и
  учётка те же, Kerberos-аутентификация проходит прозрачно, ничего доп. настраивать не нужно.

Кнопка "Проверить подключение" рядом с полем делает пробный `Get-DnsServerZone` и
показывает в логе, получилось достучаться или нет.

Оставь поле пустым — и всё вернётся к работе с локальным сервером, как раньше.

## Подтверждение удаления

Удаление одиночной записи (A/AAAA/CNAME/...) — обычное окно "да/нет", без лишней драмы.

Удаление **зоны, scope, подсети или политики** — усиленное окно (`DangerConfirmDialog.cs`):
крупный красный текст с описанием последствий, кнопка "Удалить" заблокирована первые
5 секунд с видимым отсчётом (5...4...3...2...1) — специально, чтобы нельзя было кликнуть
на автомате не глядя. Кнопка "Отмена" активна сразу.

## Списки с перетаскиваемой границей

На вкладках "Scopes и записи" и "Политики" граница между двумя панелями (списком и
деталями/записями) — перетаскиваемая (`SplitContainer`). Позиция сохраняется в
`settings.ini` рядом с exe и восстанавливается при следующем запуске (по ключам
`ScopesRecordsSplitter` и `PoliciesSplitter`). Если файл настроек недоступен или
повреждён — просто используется позиция по умолчанию, ничего не падает.

## Сортировка, фильтр и экспорт списков

На вкладках "Зоны" и "Scopes и записи" (список записей) есть:
- **Фильтр** — текстовое поле, список сужается по мере ввода (ищет по всем видимым полям
  строки: имени, типу, значению/метке). Работает мгновенно, без обращения к серверу —
  фильтрует то, что уже загружено.
- **Сортировка** — выпадающий список поля (Имя/Тип/[Значение]) + кнопка ▲/▼ для смены
  направления.
- **Экспорт в файл...** — сохраняет то, что сейчас реально отображено в списке (то есть
  уже с учётом фильтра и сортировки) в `.txt`, путь выбирается стандартным диалогом
  сохранения. Есть также на вкладке "Подсети".

Важно для записей в scope: сортировка/фильтр меняют порядок строк на экране, но не путают
удаление — приложение ведёт отдельный список "что сейчас реально показано" и удаляет именно
ту запись, что выбрана, а не то, что было бы по номеру в исходном (несортированном) ответе сервера.

## Источник зоны

На вкладке "Зоны" под списком — полоса с информацией об источнике выбранной зоны:
- для `Primary` — AD (домен) или файл (`.dns`, с указанием имени);
- для `Secondary`/`Stub` — список мастер-серверов (`MasterServers`), с которых зона
  реплицируется. Такую зону нельзя редактировать здесь вообще — редактировать нужно
  на одном из перечисленных мастеров (см. раздел про "Целевой DNS-сервер" выше).

## История удалённых серверов

Поле "Целевой DNS-сервер" запоминает последние 10 серверов, к которым приложение успешно
подключалось (и локально это не считается) — при переключении с "Локальный" на ручной
ввод сразу открывается выпадающий список с этой историей, не нужно перепечатывать адрес
каждый раз заново. Хранится в `settings.ini` рядом с exe.

## Файл лога изменений

`changes.log` лежит **рядом с exe**, создаётся автоматически при первом запуске
приложения (если уже есть — не трогается и просто дополняется). Пишутся только реальные
изменения (создание/удаление зоны, scope, подсети, политики, записи) — без "шума" от
обновления списков. Размер файла не ограничивается.

Формат строки:
```
2026-07-16 14:04:32 | OK     | RECORD ADD    | зона/объект: corp.local | Scope=... A test -> 10.0.0.1 | пользователь: admin
```

Кнопка "Открыть файл лога изменений" в панели вывода открывает файл в ассоциированной
программе (обычно блокнот).

## Диагностика ошибок

- Если PowerShell-командлет бросает исключение, в лог попадает **вся цепочка**
  `InnerException` плюс, через рефлексию, доп. поля вроде `StatusCode`/`NativeErrorCode`/
  `ErrorData` (там у CIM-исключений обычно прячется настоящая причина, а не generic-фраза
  "Не удалось создать запись ресурса...").
- Если после запроса политики поле подсети/scope пустое — приложение автоматически
  выводит в лог **все реальные свойства** объекта, чтобы можно было увидеть точные
  имена без гаданий (см. историю про `Criteria`/`Content` выше).
- **"Эта машина не DNS-сервер" (v2.2.3, фикс дублирования и цвета в v2.2.4)**: если при
  локальном вызове (без указания "Целевой DNS-сервер") прилетает `WIN32 1722 "Сервер RPC
  недоступен"` — это почти всегда значит, что на этой машине не установлена роль DNS Server
  или хотя бы RSAT: DNS Server Tools, службе просто некому ответить по RPC. Вместо сырого
  CIM-дампа приложение показывает понятную фразу с двумя вариантами действия: указать
  целевой сервер в поле сверху (если приложение запущено не на самом DNS-сервере), либо
  поставить роль/RSAT (`Add-WindowsFeature RSAT-DNS-Server`).
  При старте приложение делает **два** независимых запроса `Get-DnsServerZone` (для списка
  зон и для выпадающих списков) — если первый явно провалился с этой же причиной, второй,
  заведомо обречённый на тот же исход, больше не выполняется (раньше сообщение дублировалось
  дважды подряд). Сама фраза также получила префикс `ОШИБКА:` — без него общий механизм
  определения успеха/провала (`WasSuccess`) не распознавал бы её как ошибку, и она бы
  показывалась серым текстом вместо красного, как будто запрос прошёл нормально.

## Что можно доделать под себя

- Просмотр/удаление записей вне scope (прямо в самой зоне, без привязки к scope) —
  добавляется по аналогии с уже готовым кодом для scope-записей.
- Поддержка остальных типов записей (NS, MX и т.д.) — паттерн уже есть в `AddRecordToScopeAsync`,
  просто добавить ещё один `case` с нужным командлетом/параметром.
- Валидация ввода (IP-адреса, CIDR) минимальная — ошибки формата прилетят в блок вывода
  как есть от PowerShell/DNS-сервера.
